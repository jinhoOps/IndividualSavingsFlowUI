# 결과 이미지 저장 용량·자동 삭제 설계

**상태:** 2026-09-22 사용자 요청에 따른 검토용 설계. 아직 구현·운영 적용하지 않았다.
**목적:** 공유 이미지가 누적되어 사용자가 정한 500MB 예산을 침범하지 않도록 업로드 전에 제한하고, 만료된 실제 파일을 삭제한다.
**실행 문서:** [구현 계획](../plans/2026-09-22-result-card-storage-budget.md)
**기존 계약:** [결과 이미지 공유](../plans/2026-09-21-result-image-link-sharing.md), [운영 적용 절차](../../supabase-account-setup.md#2026-09-21-결과-이미지-공유-적용)

## 1. 확인된 현재 상태

- 미리보기와 기기 저장은 브라우저에서 처리한다. `공유 링크 만들기`를 눌렀을 때 완성된 PNG만 서버에 업로드한다.
- 현재 원본은 private Storage, 파일당 5MiB, 계정당 최근 24시간 예약 20회, 게시 후 48시간 만료를 사용한다. 전체 바이트 제한은 없다.
- 삭제 함수 원본은 있으나 운영 Cron 등록·실행, 실제 Storage 사용량은 확인되지 않았다. 웹앱 배포 성공은 이 운영 검증을 대신하지 않는다.
- 현재 삭제 함수는 한 번에 최대 100개를 조회한다. 업로드 예약과 quota 확인은 하나의 DB 트랜잭션이 아니며, 계정 삭제 시 메타데이터 cascade로 파일 추적을 잃을 수 있다.
- [직전 이미지 검증](../evidence/2026-09-22-result-card-and-leave-guard.md)의 PNG 두 개는 166,789B와 219,561B였다. 모든 입력·기기에서의 최대 크기를 뜻하지 않는다.

Supabase Free의 공식 표기는 **DB 500MB, 파일 Storage 1GB**로 서로 다른 항목이다. 이 설계는 요금제 한도와 별개로 사용자가 요청한 **이미지 운영 예산 500MB**를 적용한다. DB·전송량도 별도로 확인한다. [공식 가격표](https://supabase.com/pricing) (2026-09-22 확인).

## 2. 정책 제안

모든 MB는 1,000,000바이트인 십진 단위다.

| 항목 | 제안 값 / 동작 |
| --- | --- |
| 이미지 예산 | 500,000,000B |
| 신규 공유 허용 상한 | 예약과 미삭제 파일을 합쳐 400,000,000B |
| 여유 공간 | 100,000,000B: 기존 파일·미확인 객체·운영 오차 확인 여유 |
| PNG 한 개 | 최대 1,000,000B, 1080×1440, PNG |
| 사용자 제한 | 최근 24시간 생성 예약 20회, 같은 요청 재시도는 추가 차감 없음 |
| 보관 기간 | 기본 48시간, 운영자가 새 공유에 한해 24시간으로 변경 가능 |
| 삭제 주기 | 5분, 성공 heartbeat가 15분 이상 없으면 신규 생성 중지 |
| 예약 처리 기한 | 생성 후 15분; 이후 게시·재업로드 불가 |
| 용량 대조 | 매일 Storage 목록 전체를 페이지별 조회해 예약 장부와 대조 |

상한은 `result-card-shares` 전용 bucket에 적용한다. 운영 활성화 전 **다른 bucket을 포함한 프로젝트 Storage 사용량**도 확인한다. 다른 용도의 저장량을 O바이트로 유지해야 한다면 이미지 상한은 `min(400,000,000, max(0, 500,000,000 - O - 100,000,000))`로 낮춘다. 다른 업로더가 제한 없이 쓰는 프로젝트 전체에 대해서는 이 기능만으로 500MB 이하를 보장할 수 없다. 미확인 객체나 외부 쓰기가 발견되면 신규 공유를 중지하고 예산을 재산정한다.

### 24시간으로 줄이는 기준

시간 단축만으로 전체 용량을 제한할 수 없으므로 바이트 상한을 먼저 구현한다. 기본 48시간은 유지하되 다음 중 하나가 나타나면 운영자가 24시간 전환을 검토한다.

- 최근 24시간에 게시한 PNG 바이트 합계 × 2가 300MB를 넘는다.
- 최근 게시 이미지 크기의 p95가 500KB를 넘는다. 표본 수와 실제 사용량을 함께 기록한다.
- 정상적으로 정리 중인데도 용량 부족으로 신규 공유가 반복 차단된다.

삭제 장애는 보관 기간 변경으로 처리하지 않는다. 먼저 삭제를 복구한다. 기간 변경은 **이후 게시하는 링크에만** 적용하고, 기존 `expires_at`은 단축·연장하지 않는다. 자동 기간 전환과 화질 저하는 이번 범위에서 제외한다.

## 3. 생성과 용량 예약

### 최소 데이터 변경

기존 공유 테이블에 `byte_size`, `content_sha256`, `upload_settled_at`, `deleted_at`을 추가하고 상태를 `pending | ready | deleting | deleted`로 확장한다. `owner_id`는 nullable + `ON DELETE SET NULL`로 바꾼다. 계정 삭제 시 파일 경로·바이트를 남겨 삭제를 끝낼 수 있게 한다. 소유자가 없는 공유는 즉시 열람을 거부한다.

단일 정책 행에 `capacity_bytes`, `retention_hours`(24 또는 48), `creation_enabled`, `last_cleanup_success_at`, `last_inventory_success_at`, `inventory_valid`를 저장한다. 초기에는 생성 비활성화다. 정책과 RPC는 service role만 접근한다. 일반 anon/authenticated 직접 접근은 금지한다.

용량은 `deleted`가 아닌 행의 `byte_size` 합계로 계산한다. 별도의 누적 counter를 두지 않는다. 만료되었거나 삭제 실패한 행도 포함한다. 기존 메타데이터에 없는 객체는 장부 대조가 완료될 때까지 신규 생성을 막는다.

### 요청 순서

1. 서버에서 인증·request UUID·token·MIME를 검사한다. `Content-Length`가 크면 즉시 거부하고, 헤더가 없거나 거짓이어도 스트림 누적 1,000,001번째 바이트에서 중단한다.
2. 실제 PNG signature/IHDR·치수·바이트 수를 검사하고 SHA-256을 계산한다. 클라이언트가 보낸 크기를 신뢰하지 않는다.
3. 예약 RPC에서 정책 행을 `FOR UPDATE`로 잠근다. `(owner_id, request_id)`와 token/hash/body hash의 동일성을 먼저 검사한다.
4. 새 예약에만 생성 활성화, cleanup freshness, 24시간 이내 성공한 inventory, 일일 횟수와 바이트 여유를 검사하고 `pending`을 insert한다. 이 전체가 한 트랜잭션이다. 수신 순서가 겹쳐도 상한을 넘겨 예약하지 못한다.
5. **새 예약을 얻은 호출 하나만** 고정된 무작위 object path에 `upsert:false`로 업로드한다. 재시도는 업로드를 다시 시작하지 않는다.
6. 성공 응답을 받은 후 조건부 게시 RPC로 `pending → ready`, `upload_settled_at`, 서버 `published_at`, `expires_at`을 기록한다. 게시 시점의 정책 24/48시간을 한 번만 적용한다.
7. 저장 응답이 불명확하거나 게시 RPC가 실패하면 예약을 그대로 유지한다. 정상 링크를 반환하지 않는다. 후속 정리가 파일과 예약을 회수한다.

이미 `ready`인 동일 요청은 기존 링크·만료를 반환한다. `pending`인 동일 요청은 `202 share_pending`과 `Retry-After`를 반환한다. 만료·삭제 상태는 `410 share_expired`이며 같은 요청을 부활시키지 않는다. 같은 request/token에 다른 내용은 `409 request_conflict`다. 이 검사는 용량·횟수 제한보다 앞서므로 응답만 유실된 성공 요청을 재시도할 수 있다.

## 4. 만료·삭제·장애

### 열람과 삭제를 분리

GET은 `ready`, 소유자 존재, 서버 시각이 `expires_at` 이전인 경우만 허용한다. 다운로드 후 응답 직전에도 만료를 확인한다. 만료 시각 이후 새 열람은 Cron 지연과 관계없이 차단한다.

Storage 파일 삭제는 반드시 Storage API를 사용한다. SQL로 `storage.objects` 행만 지우면 실제 파일이 남을 수 있다. [공식 삭제 문서](https://supabase.com/docs/guides/storage/management/delete-objects).

### 정리 순서

1. 5분 Cron은 만료된 ready, 소유자가 사라진 행, 15분 지난 pending, 이전 삭제 실패 행을 조회한다. `(정리 대상 시각, id)` 순서의 cursor로 100개씩 처리하며 호출당 45초 작업 예산을 둔다. 실패한 앞쪽 100개가 뒤쪽 정리를 막지 않게 다음 cursor로 진행한다. 제한 시간에 걸리면 서버 정책 행에 cursor를 저장해 다음 호출이 이어받고, 전체 순회 후 처음으로 돌아온다.
2. 조건부 상태 전환으로 `deleting`을 표시한다. 이 상태에서는 게시와 재업로드가 모두 금지된다. 중복 Cron의 같은 파일 삭제는 멱등적으로 처리한다.
3. Storage API 삭제가 성공하고 객체 부재를 확인한 **완결된 업로드**만 `deleted`로 바꾸어 용량을 반환한다. 삭제 실패·확인 실패는 용량을 유지한다. 이미 없는 파일은 동일 조건에서 성공으로 처리한다.
4. 함수가 중단되어 업로드 완료 여부가 불명확한 예약은 파일을 정리하더라도 자동으로 용량을 반환하지 않는다. `deleting` 상태로 남겨 일일 대조에서 보고한다. 운영자는 신규 쓰기를 중지하고 진행 중 쓰기가 종료된 근거를 확보한 뒤 재대조하여 해제한다. TTL 경과나 한 번의 404만으로 진행 중 업로드 종료를 추정하지 않는다.
5. 삭제 완료 행은 `max(created_at + 24시간, deleted_at + 24시간)`까지 보존한다. 실제 파일 바이트는 0으로 계산하면서 일일 예약 횟수·지연 재시도 응답을 유지하고, 기한 후 행을 제거한다.
6. 목록 조회와 삭제 요청이 오류 없이 끝난 주기에 heartbeat를 갱신한다. 대상 0개도 성공이다. 오류가 있으면 갱신하지 않는다. backlog 수와 가장 오래된 대상 시각을 함께 기록한다.

Supabase Edge worker의 현재 최대 수명은 Free 150초, Paid 400초다. 이는 Storage 쪽 요청 완료를 보증하지 않으므로 예약 해제의 유일한 근거로 사용하지 않는다. [공식 함수 제한](https://supabase.com/docs/guides/functions/limits).

### 대조·관찰

- 하루 한 번 동일 정리 함수의 inventory 모드로 bucket의 전체 객체 경로·크기와 장부를 대조한다. 작업이 45초를 넘으면 서버 정책 행에 cursor를 저장하고 다음 5분 cleanup 호출에서 대조를 이어간다. 쓰기 중 행을 고려해 확인되지 않은 차이는 재검사하며, 해결 전 `inventory_valid=false`로 신규 생성을 차단한다.
- 오래된 미추적 경로는 곧바로 삭제하지 않는다. 기존 공유·진행 중 업로드와 연결되지 않는지 확인하고 관리 대상인 것을 확정한 뒤 Storage API로 제거한다. 기존 1MB 초과 파일도 만료 전에는 보존하고 실제 크기를 예산에 넣는다.
- 기록은 현재 예약 바이트, 실제 객체 바이트, 정리 대기·실패 수, 미확인 예약 수, 마지막 성공 시각, 24시간 게시량·크기 분포로 한정한다. token·이미지·원화 수치·종목명은 로그에 남기지 않는다.
- 별도 모니터링 서비스를 추가하지 않는다. 일별 집계와 작업 로그는 7일 보존 후 정리하며 DB 크기, Storage, egress를 운영 점검표에 구분한다.

## 5. 사용자 경험과 브라우저 자원

| 상황 | 화면 동작 |
| --- | --- |
| 정상 | 미리보기 → 명시적 링크 생성 → 서버가 준 정확한 만료 시각 표시 |
| 생성 전 기간 안내 | `공유 링크는 최대 2일 동안 열 수 있어요. 정확한 만료 시각은 생성 후 표시돼요.` |
| 1MB 초과 / 413 `image_too_large` | `이미지가 커서 링크로 공유할 수 없어요. 이미지로 저장해 주세요.` |
| 일일 제한 / 429 `daily_limit` | 재시도 가능 시각 표시, `이미지 저장` 제공 |
| 용량·정리 장애 / 503 `capacity_reached` 또는 `cleanup_unhealthy` | `지금은 공유 링크를 만들 수 없어요. 이미지로 저장해 주세요.` |
| 같은 요청 진행 중 / 202 `share_pending` | 준비 중 상태, 자동 무한 재시도 없이 수동 재시도 가능 |
| 폐기된 요청 / 410 `share_expired` | 새 링크 만들기 동작에서 request UUID와 token을 새로 생성 |

원본 해상도·글꼴 비율을 줄여 억지로 1MB에 맞추지 않는다. 공유 실패는 workspace 수정·dirty 상태를 만들지 않는다. 서버 용량 상세를 일반 사용자 화면에 노출하지 않는다.

PNG blob URL은 교체·화면 종료 때 해제한다. 이미지 응답은 `Cache-Control: no-store`, Service Worker 이미지 캐싱 제외를 유지한다. IndexedDB/localStorage에 PNG를 보관하지 않는다. 수신 화면은 만료 timer와 foreground 복귀 시 재검사하여 표시 중인 이미지도 해제한다. 기기에 다운로드했거나 메신저가 복제한 사본까지 회수한다는 의미는 아니다.

## 6. 적용·검증과 범위

적용 순서는 신규 생성 중지 → 운영 현황·기존 파일 inventory → migration과 기존 크기 backfill → 함수 배포 → Cron 두 주기 및 inventory 성공 → 인증된 시험 공유 → 생성 활성화다. 예산 초과 상태에서는 기존 유효 링크를 임의 삭제하지 않고 만료 정리 후 활성화한다.

필수 증거는 동시 예약 한도, 중복 재시도, 삭제 실패 시 바이트 유지, pending/삭제 경합, 계정 삭제 후 실제 파일 제거, 기존 5MiB 계약 파일의 보존, 24/48시간 신규 링크 차이, 390/768/desktop 안내·저장 대안이다. 실제 Storage API·Cron 검증과 시간 가속 테스트를 구분하고, 실제 48시간 만료 증거가 생기기 전까지 그 항목은 미완료로 남긴다.

문제 발생 시 `creation_enabled=false`로 생성만 중단하고 정상 링크 읽기와 정리는 유지한다. 기존 무제한 writer로 되돌리지 않는다. 원격 접근 정보가 없는 현재 단계에서 운영 사용량·Cron 성공을 추정하지 않는다.

Main/Simulation/Portfolio 소유권, schema v5, protocol 5, Account Map·locations 보존, backup·restore 계약은 변경하지 않는다. 이번 범위는 이미지 저장 정책과 그 실패 UX이며 이전에 수정한 글자 렌더링·이탈 확인 로직을 다시 설계하지 않는다.
