# 커뮤니티 답글·멘션·알림·탐색 확장 설계

**상태:** 2026-09-28 사용자 승인에 따라 구현·운영 DB/job·PR #33/Pages 출시·전체 검증 완료. 앱 내 알림함과 댓글 밀도, 동일 자산군 종목 경계선을 포함한다.

**목표:** 공유한 투자 비율에 관해 대화를 이어가고, 게시물이 늘어도 원하는 구성을 찾으며, 답글과 멘션을 놓치지 않는다.

현재 기준은 [PRD](../../ways-of-work/plan/isf-rebuild/connected-financial-planning-workspace/prd.md), [커뮤니티 기본 설계](2026-09-28-portfolio-lounge-design.md), [댓글·공감 설계](2026-09-28-lounge-community-design.md), [DESIGN](../../../DESIGN.md)다. 이 문서는 기존의 답글·알림·공감순 제외 범위를 확장하는 제안이다. 구현·승인 전까지 현재 제품 계약은 기존 문서를 따른다.

**구현 상태:** 구현과 운영 적용 증거는 [대화](../evidence/2026-09-28-community-conversation.md)·[탐색](../evidence/2026-09-28-community-discovery.md)에 기록한다. 대화·검색·정렬은 한 번의 프런트 출시로 통합한다.

## 1. 현재 구현과 부족한 부분

| 영역 | 현재 확인한 동작 | 확장할 부분 |
| --- | --- | --- |
| 게시물 | 갱신시각+ID 커서, 12개씩 더 보기, 전체/내 공유 | 서버 검색·필터, 순서가 안정적인 정렬 |
| 댓글 | 최신순 20개, 이전/다음, 본인 삭제 | 답글 묶음, 특정 댓글로 이동 |
| 공감 | 이모지별 인원, 중복 제거 인원 내부 집계 | 공감 많은 순의 정렬 기준으로 사용 |
| 닉네임 | 2~20자, `- . @` 허용, 변경 후 48시간 제한 | 이름 변경에도 동일 사용자를 가리키는 멘션 |
| 갱신 | 보이는 온라인 화면에서 30초, 조작 중 화면 보존 | 알림 수·답글 수 갱신, 검색 조건·정렬 순서 보존 |
| 규모 | 사용자당 게시물 1개, 게시물/프로필 각각 최대 5,000개 | 상한 내 성능 측정과 이후 상한 변경 판단 |

## 2. 접근 방식과 구현 순서

| 선택 | 장점 | 비용/한계 |
| --- | --- | --- |
| 답글만 먼저 | 작게 배포 가능 | 멘션 대상·알림·댓글 링크를 다시 연결해야 함 |
| **대화 기능 → 검색·필터 → 정렬** | 각 단계가 완결되고 DB/UX를 검증하기 쉬움 | 단계별 검증 후 한 프런트 출시 |
| 소셜 기능 전체 동시 개발 | 기능 범위가 넓음 | 팔로우·추천·피드 개인화까지 범위가 커짐 |

두 번째를 추천한다. 실행 계획은 [대화·알림](../plans/2026-09-28-community-conversation.md)과 [탐색](../plans/2026-09-28-community-discovery.md)으로 나눈다. 팔로우, DM, 이메일/푸시 알림, 실적·예상 수익률 순위, 이미지 업로드는 이번 범위에 포함하지 않는다.

## 3. 답글 UX

### 배분 막대의 종목 경계 — 추가 사용자 요청

- 커뮤니티 카드·상세·게시 미리보기·가져오기에서 같은 자산군의 종목도 각 비율 길이로 나눈다. 자산군 색상과 주식/현물/채권/현금/기타 범례는 유지한다.
- 종목 사이에 1px의 낮은 대비 내부 구분선을 둔다. gap이나 최소 너비로 비율 길이를 바꾸지 않고, 아주 작은 구간도 원래 비율을 유지한다. 추가 hover·tooltip·애니메이션으로 시선을 끌지 않는다.
- 자산군별로 모으고 그 안에서는 기존 종목 순서를 유지한다. 하나의 자산군에 여러 종목이 있어도 색상은 같다. 정확한 종목명·비율은 기존 목록에서 읽는다.

- 들여쓰기는 한 단계다. 원댓글에 `답글`과 `답글 N개 보기`를 둔다. 펼치기 전에는 답글 본문을 요청하지 않는다.
- 원댓글은 최신순 20개, 한 원댓글의 답글은 오래된 순 10개씩 `답글 더 보기`로 읽는다. 답글에 답할 때도 같은 묶음에 추가하고 `○○님에게 답글`로 상대를 구분한다.
- 하단의 기존 입력창 하나를 재사용한다. 답글 선택 시 입력창 위에 상대·원문 한 줄·취소를 표시하고 입력창으로 초점을 옮긴다. 이미 쓴 글은 유지한다.
- 대상을 바꿔도 본문은 유지한다. 대상 선택만 한 빈 입력은 이탈 확인을 띄우지 않는다. 실패 시 본문·멘션·답글 대상을 유지한다.
- 답글을 등록하면 해당 묶음만 갱신하고 등록한 답글을 보여준다. 이전 답글 전체를 자동으로 불러오지 않고 서버가 반환한 마지막 구간으로 이동한다. 다른 묶음·입력 초점을 보존한다.
- 카드의 댓글 수는 삭제되지 않은 원댓글+답글 합계다. 원댓글 옆 답글 수는 삭제되지 않은 답글만 센다.
- 본문을 삭제하면 즉시 지운다. 다른 사용자의 답글이 남은 원댓글은 `삭제된 댓글입니다`라는 자리만 유지한다. 다른 답글이 참조하는 답글도 본문 없는 자리로 남기고, 참조와 하위 답글이 없으면 물리 삭제한다.
- 계정 삭제도 해당 사용자의 댓글 본문·닉네임·멘션 메타데이터·알림을 지운다. 다른 사람이 쓴 답글을 보존하기 위한 자리에는 원래 계정 식별자를 남기지 않는다. 게시물 삭제는 전체 대화·관련 알림을 cascade 삭제한다. 이는 기존 댓글의 단순 계정 cascade 계약에서 바뀌는 부분이다.
- 공통 `ResponsiveDialog`를 유지한다. 모바일 88dvh 시트, 웹 중앙 모달, 기존 400~500ms Anime.js, 비입력 영역 drag, 초점 복귀·reduced motion을 따른다. 답글용 중첩 모달은 만들지 않는다.

### 댓글 모달 밀도 — 추가 사용자 요청

```text
댓글 26                                      [닫기]
포트폴리오 제목 한 줄
닉네임 · 09:40                         [답글] [⋯]
댓글 본문. 박스 없이 바로 읽는 영역
  답글 닉네임 · 09:42                   [답글] [⋯]
  @상대 이어지는 본문
  [답글 3개 더 보기]
─────────────────────────────────────────────────
○○님에게 답글                                [취소]
[댓글 입력 · 기본 2줄, 작성 시 최대 4줄까지 확장   ]
[@]                                0/500 [등록]
```

- 댓글마다 카드·큰 배경·둥근 테두리를 반복하지 않는다. 메타 정보·답글·더보기는 같은 행, 본문은 바로 아래로 묶는다. 본인 삭제는 44px 더보기 메뉴 안에 두며 타인 댓글에는 빈 메뉴를 만들지 않는다.
- 원댓글 위아래 padding 각각 10px, 메타/본문 gap 4px, 답글 위아래 padding 각각 8px, 답글 들여쓰기 12px를 시작값으로 한다. 얇은 구분선은 원댓글 묶음 사이에만 둔다. 실제 화면을 보며 간격을 조정하되 터치 영역은 줄이지 않는다.
- 본문 14~15px·줄높이 1.45~1.55, 보조 시간 12px 이상, 입력 16px를 유지한다. 본문을 임의 줄 수로 잘라 숨겨서 밀도를 높이지 않는다. 긴 닉네임만 말줄임하고 접근성 이름은 온전히 제공한다.
- 헤더는 `댓글 N`과 게시물 제목 한 줄로 압축한다. 반복 안내문·본문 위 추가 제목은 제거하고 입력 label은 접근성용으로 보존한다.
- 입력창은 기본 2줄, 최대 4줄 뒤 내부 스크롤이다. 작성 대상 표시가 필요할 때만 한 줄 추가한다. 글자 수와 등록 버튼을 같은 하단 행에 두고 긴 고정 footer를 만들지 않는다.
- 모바일 390×844, 키보드가 닫힌 상태, 한두 줄 원댓글 fixture에서 **첫 화면에 최소 5개 원댓글 본문이 읽히는 것**을 목표로 확인한다. 긴 글과 화면 확대에서는 자연스럽게 높이가 늘어나야 한다. 200% 확대·작은 높이에서는 개수 목표보다 읽기/조작/입력 가시성을 우선한다.
- 키보드가 열리면 보이는 viewport 안에서 header/footer를 유지하고 본문이 스크롤한다. 기존 시트 drag는 댓글 빈 공간에서 가능하고 textarea·멘션 후보·메뉴·스크롤 조작과 충돌하지 않아야 한다.

## 4. 사용자 멘션

- 댓글·답글에서 사용자 선택으로 멘션한다. 입력의 `@` 버튼 또는 새 멘션 시작 입력이 입력창 위의 인라인 검색 영역을 연다. 이 영역의 검색 입력과 후보 목록에 combobox 키보드 규칙을 적용한다.
- 후보를 선택하면 본문에 `@닉네임`과 연결 정보를 넣는다. 그냥 타이핑하거나 붙여넣은 `@문자열`은 일반 텍스트다. 본문의 이메일이나 닉네임 안 `@`를 자동 멘션으로 바꾸지 않는다.
- 빈 검색은 해당 글 작성자·대화 참여자 최대 5명만 보여준다. 전체 사용자 검색은 두 글자부터 접두어로, NFC·영문 대소문자 무시, 최대 5명, 300ms 지연 및 IME 조합 완료 후 실행한다. 자신은 후보에서 제외한다.
- 한 댓글에서 최대 3명의 명시적 멘션을 허용한다. 같은 사용자 반복 선택은 하나로 합친다. 답글 상대 표시는 이 한도 밖의 별도 관계다.
- `lounge_profiles`에 Auth UID와 다른 무작위 `public_id`를 추가한다. 검색 응답은 `publicId, nickname`만 반환한다. 이메일·Auth UID·자산·workspace를 사용자 검색에 포함하지 않는다.
- 닉네임 변경에도 `public_id` 연결은 유지한다. 본문에는 작성 당시 표기를 보존하고 조회 응답의 별도 `currentNickname`으로 선택 영역을 렌더링한다. 닉네임을 다른 사람이 재사용해도 옛 멘션이 새 사용자에게 연결되면 안 된다.
- 본문+멘션 범위(`start`, `end`, `publicId`, `label`)를 저장한다. 범위는 Unicode code point 기준이고 겹침·본문 불일치·없는 대상·3명 초과를 서버에서 거부한다. UTF-16 커서와 code point 변환은 프런트 경계에서 처리한다.
- 연결된 텍스트 내부를 편집하면 그 멘션 연결을 해제한다. 앞부분 편집은 범위를 이동한다. 잘라내기·붙여넣기·실행 취소에서도 다른 사람에게 잘못 연결되지 않아야 한다.
- 검색 후 저장 전 닉네임이 바뀌면 재선택을 안내하고 작성 내용을 보존한다. 이미 성공한 같은 UUID 재시도는 저장된 요청과 비교하므로 이후 이름 변경에 영향받지 않는다.
- 사용자가 삭제되면 그 멘션 문자열을 `@탈퇴`로 치환하고 연결/알림을 제거한다. 원래 닉네임은 2자 이상이므로 이 치환으로 본문 길이 상한이 증가하지 않는다. 그 범위의 옛 닉네임도 scrub하고 나머지 멘션의 offset을 조정한다. 주변 일반 텍스트는 변경하지 않는다.

## 5. 앱 내 알림함

- 커뮤니티 상단 오른쪽 공유 action 옆에 44px 종 버튼과 안 읽은 개수(`99+`)를 둔다. 닉네임 변경은 계속 관리 메뉴에 둔다. 390px에서는 공유 문구를 `공유`로 줄이고 접근성 이름은 유지한다.
- 알림은 `내 댓글/답글에 대한 답글`, `나를 명시적으로 멘션` 두 종류다. 일반 새 댓글·공감은 알림을 만들지 않는다.
- 같은 댓글에서 답글 상대이면서 멘션 대상이면 수신자별 한 행만 만들고 멘션 유형을 우선한다. 본인에게는 알리지 않는다. 같은 작성 요청 재시도에도 한 행만 생긴다.
- 최신순 20개씩 조회한다. `전체 / 안 읽음`, 개별 읽음, `모두 읽음`을 제공한다. 알림함을 열기만 해서는 전부 읽음 처리하지 않는다.
- 클릭하면 같은 dialog에서 해당 게시물의 댓글 단계와 원댓글 묶음을 연다. 대상이 20개 밖이어도 직접 조회하고 잠깐 강조한다. 전체 댓글을 순회해서 찾지 않는다. 뒤로 가면 알림 목록의 위치로 돌아간다.
- 읽음 처리는 명시적 상태 변경으로 재시도 가능하다. `모두 읽음`은 알림함 조회 응답의 서버 cutoff와 당시 존재한 미읽음 ID 집합(최대 100개)을 함께 보낸다. 시간만으로 대상을 정하지 않아, 더 일찍 시작했지만 조회 뒤에 commit된 알림도 읽음으로 만들지 않는다.
- 알림함은 게시물·댓글을 참조하고 제목·본문·닉네임을 별도로 복제하지 않는다. 삭제/탈퇴가 발생하면 목록에서 제거한다. 이미 클릭한 뒤 사라지면 설명과 목록 복귀 action을 제공한다.
- 최근 30일 이내·사용자당 최대 100개·전역 최대 20,000개만 보관한다. 상한에 닿으면 오래된 알림부터 제거하므로 30일 보관을 보장하지 않는다. 매일 정리하고 삽입 전에도 상한을 집행한다.
- 30초 조용한 갱신에 미읽음 개수를 합친다. 알림함을 열었을 때만 목록을 읽는다. 숨긴 탭·오프라인에서는 멈추고, 알림 확인 때문에 토스트·소리·스크롤 이동을 반복하지 않는다.

## 6. 카드 탐색 UX

### 화면 배치

```text
내 닉네임                             [알림] [공유]
[ 제목 · 종목 · 닉네임 검색                    지우기 ]
[전체] [내 공유]                 [최근 수정순 ▾] [필터]
[선택한 조건 ×] [선택한 조건 ×]            [초기화]
카드 목록
                     [더 보기]
```

- 반복되는 큰 제목은 추가하지 않는다. 검색은 한 줄, 정렬·필터는 오른쪽, 적용 중인 조건만 아래 칩으로 노출한다. 필터 열기는 공통 모바일 시트/웹 모달이다.
- 검색 대상은 제목·메모·종목명·현재 닉네임이다. 전체 서버 데이터에서 검색하고 현재 내려받은 카드만 필터링하지 않는다.
- 첫 버전은 입력 전체를 하나의 부분 문자열로 취급한다. 공백 정리·NFC·영문 소문자를 적용하고 1~80자를 허용한다. 한 글자 `금`도 검색 가능하다. `%`, `_`, 역슬래시는 와일드카드가 아니라 문자 그대로 검색한다.
- 낮은 화면에서는 멘션 후보를 작성 영역 위에 겹쳐 제한 높이로 열고 목록만 스크롤한다. 입력·등록 action이 화면 밖으로 밀리지 않게 한다.
- 검색은 조합 완료 후 350ms, Enter는 즉시 요청한다. 진행 중에는 입력 옆 작은 상태만 표시하고 응답 전 기존 카드를 유지한다. 다른 검색/정렬의 늦은 응답은 버린다.
- 첫 필터는 `전체/내 공유`, 최근 수정 `전체/7일/30일`, `현금 포함`, 자산 규모 구간(다중 선택, 미공개 포함)이다. 자산 규모는 기존 공개 구간만 사용하며 숨긴 실제 금액으로 분류하지 않는다. 같은 필터 안은 OR, 서로 다른 필터는 AND다.
- 필터는 선택 초안을 유지하다 `적용`에서 한 번 요청한다. 닫기는 적용 전 조건을 버리며 재무 입력처럼 이탈 확인을 띄우지 않는다. 취소 시 결과와 위치가 유지된다.
- 이름으로 추정한 주식/현물/채권 분류는 현재 화면 보조 정보다. 이를 정확한 필터라고 제공하려면 종목 분류 계약이 먼저 필요하므로 첫 배포에서는 제외한다. 이후 명시적인 분류와 `기타` 처리 계약을 갖춘 뒤 추가한다.
- 빈 전체 목록, 검색 결과 없음, 필터 결과 없음, 요청 실패를 구분한다. 조건 없음으로 되돌리는 버튼과 재시도를 제공한다. 전체 결과 수는 매 폴링마다 계산하지 않는다.

### 페이지와 상태 복원

- 모바일/웹 모두 12개 `더 보기`를 유지한다. 서버는 13개를 조회해 `hasMore`를 정확히 계산한다. 필터마다 결과 수가 바뀌는 상황에서 임의 번호 페이지를 먼저 도입하지 않는다.
- 검색·필터·정렬이 바뀌면 커서를 폐기하고 첫 페이지부터 조회한다. 데이터가 없는 커서·다른 조건의 커서·잘못된 정렬값은 서버도 거부한다.
- 상세를 닫으면 검색 조건·펼친 페이지·스크롤·원래 카드 초점이 유지된다. URL에는 allowlist된 검색/필터만 기록하고 `post` 및 `comment` UUID를 별도로 보존한다. 새로고침은 조건부터 복원하며 이전 페이지 개수를 자동 재요청하지 않는다.
- 한 방문에서 최대 120개의 카드를 DOM에 유지한다. 10페이지 이후는 `다음 묶음 보기 / 이전 묶음 보기`로 120개 묶음을 교체하며 이동 시 목록 시작으로 간다. 무제한 DOM 누적이나 새 가상 스크롤 패키지를 추가하지 않는다.

### 정렬과 30초 갱신

| UI | 서버 순서 | 의미 |
| --- | --- | --- |
| 최근 수정순 (기본) | updated_at DESC, id DESC | 현재 구현의 의미를 명확히 표시 |
| 공감 많은 순 | 고정 집계의 distinct 반응 사용자 수 DESC, updated_at DESC, id DESC | 한 사용자의 여러 이모지는 한 명 |
| 댓글 많은 순 | 고정 집계의 살아 있는 댓글+답글 수 DESC, updated_at DESC, id DESC | 공감과 별개인 대화량 |

- 수익률·우수성·투자 추천 순위로 표현하지 않는다. 댓글 많은 순은 같은 작성자의 여러 댓글을 포함하는 단순 대화량이다.
- 최근 수정순은 첫 페이지 요청의 서버 `asOf`와 마지막 `(updatedAt,id)`를 커서에 담는다. 이후 수정·등록된 글은 다음 안전한 새로고침에서 반영한다. 삭제/수정으로 더 이상 조건에 맞지 않는 글이 빠지는 것은 허용하되 읽은 글을 재삽입하지 않는다.
- 공감/댓글 정렬은 15분마다 만든 공용 집계 세대(epoch)를 사용한다. private 집계에 게시물 ID·시각·두 집계 수만 저장하고 최신 2세대, 최대 10,000행만 보관한다. 사용자별 검색 결과/게시물 본문을 복제하지 않는다.
- 커서는 epoch·정렬 키·조건 fingerprint를 담는다. 같은 탐색에서는 동일 세대를 사용한다. 세대 만료 시 기존 카드를 남기고 `최신 순서로 다시 보기`를 제공한다. 새 세대로 몰래 이어 붙이지 않는다.
- 카드 공감/댓글 숫자는 최신 값을 보여주되 위치는 유지한다. 정렬에는 `15분마다 집계`를 보조 표시한다. 집계 작업이 실패하면 최근 세대를 유지하고 새 탐색에도 기준 시각을 표시한다. 초기 집계가 없으면 해당 정렬을 잠그고 최근 수정순을 제공한다.
- 조용한 갱신은 기본 최근 수정순·첫 묶음·목록 맨 위·검색/입력/메뉴/상세 조작 없음에서만 목록 교체를 허용한다. 나머지는 보이는 카드의 숫자와 알림 수만 갱신한다. 스크롤 중에는 카드 순서를 바꾸지 않는다.

## 7. 저장·보안·호환성

- 신규 계약은 버전이 다른 RPC/DTO로 추가한다. 기존 v1 댓글과 v2 publication 응답은 필드를 덧붙이지 않는다. strict parser를 쓰는 기존 탭/PWA가 계속 읽을 수 있어야 한다.
- 기존 댓글은 원댓글·멘션 없음으로 이관한다. 구버전 작성은 원댓글로 처리하고 구버전 목록은 살아 있는 원댓글만 기존 형태로 반환한다. 구버전 삭제 RPC도 새 삭제 규칙을 공유한다.
- 공개 댓글 DTO는 replyToAuthor(공개 ID·현재 닉네임/null)를 포함해 답글 대상이 현재 페이지 밖에 있어도 식별한다. 삭제된 대상의 이름은 노출하지 않는다.
- 댓글 확장: `root_id`, `reply_to_id`, `deleted_at`, 제한된 `mentions` JSONB. root는 같은 게시물의 원댓글만 허용하고 깊이·순환·다른 게시물 참조를 DB에서도 거부한다. 조회 인덱스는 `(post_id, created_at DESC, id DESC)` 원댓글, `(root_id, created_at, id)` 답글이다.
- 새 영속 테이블은 알림함과 작은 private 정렬 집계다. 프로필 public ID는 기존 테이블 컬럼으로 추가한다. 멘션은 댓글당 최대 3개·JSON 1KiB로 제한한다.
- 댓글 500자/2,000바이트, 게시물당 총 500행(자리 포함), 전체 20,000행, 10초 간격/24시간당 40개를 원댓글+답글에 함께 적용한다. 공감의 8종·100,000행 상한은 유지한다.
- 대화 쓰기·삭제는 동일 advisory transaction lock과 FK로 관계를 보존한다. 다른 사용자 게시물은 읽기 RLS로 확인하며 UPDATE 권한을 요구하는 행 잠금을 추가하지 않는다.
- 댓글 저장·수신자 계산·알림 삽입은 하나의 트랜잭션이다. 수신자+댓글 UNIQUE, 동일 작성 UUID 재시도, 서버 인증·시각을 사용한다. 알림 생성은 직접 호출할 수 없는 최소 권한 함수로만 허용한다.
- 각 RPC는 고정 SQL·매개변수·allowlist, 빈 search_path, 최소 권한, FORCE RLS, 직접 테이블 접근 차단을 유지한다. 알림 읽기/읽음 변경은 수신자 본인만 가능하다. 멘션 검색은 인증·프로필 필요, 최대 5개, 1분당 60회로 제한한다.
- 클라이언트의 UID·닉네임·시각·점수·수신자 배열을 권한 근거로 믿지 않는다. HTML/Markdown을 실행하지 않으며 금지문자 정규식만으로 SQLi/XSS를 막았다고 주장하지 않는다.
- DB 400MiB 신규 저장 차단을 유지한다. 삭제·읽음·알림 정리·기존 성공 재시도는 용량 차단에 걸리지 않는다. 집계 갱신도 사전 용량 검사하고 공간 부족 시 기존 세대를 유지한다.
- DB와 Storage 이미지 용량은 별도로 측정한다. 이 기능은 이미지 파일을 생성하지 않는다. DB 전체·테이블·인덱스·최대 fixture에서의 증가분을 측정하고, 정리 후 파일 크기가 바로 줄어든다고 가정하지 않는다.
- workspace schema v5/protocol 5, 백업·locations/accountMap 보존, Main 금액 소유권, 닉네임 변경 48시간, 기존 이미지 공유 만료 정책은 유지한다.

## 8. 단계별 출시·검증

1. **대화 출시:** 답글·멘션·알림함·댓글 직접 링크를 함께 검증/배포한다. 닉네임 변경·탈퇴·댓글/게시물 삭제·응답 유실·알림 중복·IME·키보드·계정 전환을 포함한다.
2. **탐색 출시:** 검색·첫 필터·커서·URL/스크롤 보존을 배포한다. 한 글자 한글·영문 티커·기호·동일시각·빠른 조건 전환·120개 묶음 경계를 검증한다.
3. **정렬 출시:** 공용 집계/정리 job·공감순·댓글순을 배포한다. 5,000 게시물/20,000 댓글/100,000 반응으로 query plan·실측 성능·용량을 남긴다. 집계/삭제 경쟁·세대 만료·job 실패를 검증한다.

각 단계는 로컬 DB 검증 → migration 전후 기존 데이터 비교 → RPC 권한/호환성 검증 → 프런트 배포 → 로그인된 운영 화면의 읽기 확인 순서다. 운영 콘텐츠를 테스트로 작성하지 않는다. 롤백은 이전 프런트로 먼저 되돌리고 additive DB와 사용자 대화는 보존한다. 정렬 실패는 정렬 UI와 job만 끌 수 있어야 한다.

390/768/1280px에서 overflow, 44px 조작 영역, 모바일 키보드/시트 containment, 초점 복귀, 스크린리더 이름, reduced motion을 확인한다. 인증 반환 경로를 바꾸는 대화 출시와 공유 라우팅을 바꾸는 탐색 출시는 전체 E2E가 필요하다.

## 9. 기술 근거

- [PostgreSQL LIMIT/OFFSET](https://www.postgresql.org/docs/current/queries-limit.html): 페이지 조회에는 유일한 정렬 순서가 필요하고 큰 OFFSET에는 비용이 든다. 이 설계는 ID 보조 키와 커서를 선택한다.
- [PostgreSQL pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html): 부분 문자열 인덱스 후보지만 짧은 검색어는 전체 인덱스 탐색이 될 수 있다. 현재 5,000행 상한에서 먼저 측정하고 자동으로 확장 기능을 추가하지 않는다.
- [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): 행 정책과 테이블 권한을 함께 검증한다.
- [WAI-ARIA Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/): 멘션 검색 입력·후보 선택에 키보드와 초점 규칙을 적용한다.
