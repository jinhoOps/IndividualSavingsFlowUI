# 주거 대출 조건·상환 일정·현금흐름

작성일: 2026-09-28. 사용자 요청으로 세 상환방식·전용 설정·그래프 구현을 진행했다. 이 문서는 월 납입액 한 칸만 추가하던 초기 제안을 대체한다. 운영 DB 적용과 Pages 배포는 별도이며 상태는 [검증 기록](../evidence/2026-09-28-housing-loan-planner.md)을 따른다.

기준: [PRD](../../ways-of-work/plan/isf-rebuild/connected-financial-planning-workspace/prd.md), [지출 도우미](2026-09-10-main-expense-assistant-design.md), [구현 계획](../plans/2026-09-28-housing-loan-planner.md).

## 문제와 범위

주거 대출을 월세에 합쳐 적으면 원금·이자를 구분할 수 없고 상환방식에 따른 월별 변화와 만기 원금을 놓치기 쉽다. Main에서 대출 조건과 예상 일정을 관리하고, 사용자가 선택한 월의 정기 납입액을 지출에 반영한다.

이번 범위는 세 상환방식, 새/기존 대출, 복수 대출, 거치기간, 현재 금리, 월별 예상 일정, 실제 정기 납입액 보정, Main 적용 및 만기 의무 표시다. 별도 대출 앱을 만들지 않는다.

은행의 일할 청구액 재현, 실제 납부 이력, 미래 금리 이벤트, 최초 Main 설정 안의 대출 하위 흐름, 대환·중도상환 시나리오와 Simulation의 상환 재원 연결은 후속 범위다. 그 기능을 제공한다고 표시하지 않는다.

## 진입과 표면

- Main 지출 금액 → 지출 계산 도우미 → 월세 다음의 주거 대출 → 대출 설정.
- 등록 뒤 Main의 대출 요약에서도 같은 설정을 바로 연다. 요약은 마지막 적용 조건을 우선하며, 아직 적용한 조건이 없으면 초안을 보여준다.
- 같은 `ResponsiveDialog`의 본문을 전환한다. 데스크톱은 중앙의 넓은 모달, 767px 이하는 최대 88dvh 공통 바텀시트다. 기존 450ms Anime.js 모션, 스크롤·손잡이·드래그·닫기 계약을 사용한다.
- 부모 답변을 유지하며 뒤로 가면 원래 위치와 초점을 복원한다. 폐기 확인 외의 모달 중첩은 없다.
- `목록 → 상환방식 → 조건 → 예상 일정` 순서다. 조건 수정은 해당 대출의 조건 화면에서 시작한다. 이전 버튼으로 방식을 다시 선택할 수 있다.
- 세 방식은 모바일에서 세로 카드, 웹에서 가로 카드다. 각 카드의 원금·이자 개념도와 오른쪽 라디오로 선택한다.

## 조건과 제한

| 조건 | 계약 |
| --- | --- |
| 이름 | 1~40자, 대출 식별용 |
| 상환방식 | 원리금균등 / 원금균등 / 만기일시 |
| 기준 | 새 대출 또는 현재 남은 원금으로 시작 |
| 원금 | 정수 원, 1원~1조 원 |
| 연 금리 | 0~100%, 소수 둘째 자리; 정수 basis points 저장 |
| 금리 유형 | 고정/변동; 변동도 현재 금리가 유지된다는 가정 표시 |
| 기간 | 전체 또는 남은 회차 1~600개월 |
| 납입월 | 첫 납입월 또는 다음 납입월; 일 단위 약정일은 받지 않음 |
| 거치 | 전체/남은 기간에 포함, 분할상환 회차가 최소 1개월 남아야 함; 만기일시는 0 |
| 대출 수 | 최대 10건, 각각 계산 후 합산 |

기존 대출은 **현재 잔액을 남은 기간으로 재산정한 예상**이다. 과거 납부를 추론하지 않는다. 조건 변경과 금리 갱신은 확인된 잔액·현재 금리로 다시 설정한다. 중도상환 이후 은행의 납입액 유지/기간 단축 약정까지 재현하지 않는다.

## 계산 계약

상환방식은 [KB국민은행 원금·이자 상환 안내](https://obank.kbstar.com/quics?cc=b104363%3Ab104516&page=C103998&prcode=LN02000003), [한국주택금융공사 상환방법 안내](https://www.hf.go.kr/ko/sub01/sub01_06_01.do)를 참고했다(2026-09-28).

`P`는 시작 원금, `r`은 연 금리/12, `n`은 거치 이후 회차다. 투자 복리의 유효 월수익률 환산을 대출에 사용하지 않는다.

| 방식 | 원금 | 이자·납입액 |
| --- | --- | --- |
| 원금균등 | P/n | 회차 시작 잔액×r, 납입액 감소 |
| 원리금균등 | 정액 납입액−이자 | 정액 A=P×r/(1−(1+r)^(-n)); 0%는 P/n |
| 만기일시 | 만기 전 0, 마지막 잔액 전부 | 평소 이자, 마지막 원금+이자 |

거치는 이자만 낸다. 계산은 **회차별 원금·이자를 정수 원으로 반올림**하고 마지막 회차에 잔액을 정산한다. TypeScript BigInt 유리수와 SQL numeric으로 같은 규칙을 구현한다. 원금 합계는 시작 원금과 일치하며 음수 잔액·NaN은 허용하지 않는다. 실제 은행의 일할·절사·휴일 이동은 다를 수 있어 `월 단위 예상`을 표시한다.

원금 1억 원, 연 4%, 120개월, 거치 없음의 첫 달 납입액은 원금균등 1,166,666원, 원리금균등 1,012,451원, 만기일시 333,333원이다. 회차별 원 단위 반올림으로 고정밀 계산을 끝까지 유지한 뒤 표시만 반올림한 결과와 다를 수 있다. 만기일시는 마지막에 원금 1억 원이 별도로 필요하다.

## 그래프와 숫자

사용자 첨부 비교 이미지의 구조를 SVG로 재구성한다. [Anime.js React](https://animejs.com/documentation/getting-started/using-with-react)와 [SVG 공식 문서](https://animejs.com/documentation/svg)를 참고하며 기존 `useAnimeScope`를 재사용한다.

- 개념도: 원리금균등은 일정한 총높이 속 증가하는 원금, 원금균등은 일정한 원금 위 감소하는 이자, 만기일시는 정기 이자와 마지막 원금으로 표시한다.
- 실제 그래프: 계산된 원금·이자의 누적 면적과 선택 회차를 표시한다. 회차 슬라이더와 월별 원금/이자/합계/잔액 내역을 제공한다.
- 만기 원금은 정기 납입 그래프의 축을 압축하지 않도록 그래프 바로 아래에 별도 표시한다. 납입 후 **예상** 잔액 0원은 실제 상환 완료나 재원 확보를 뜻하지 않는다.
- KPI는 선택 회차의 정기 납입액, 원금·이자, 납입 후 예상 잔액, 계산 시작점부터의 예상 총이자, 종료 월이다.
- 상환표는 12회차씩 선택하고 모바일에서 카드형 행으로 읽는다.
- 파란 원금/분홍 이자 범례, 축의 월, 접근성 이름을 함께 제공한다. 색만으로 구분하지 않는다.
- 개념도 450ms, 실제 그래프 500ms 표시 모션. reduced-motion이나 Anime.js 실패에서도 최종 숫자와 그래프를 즉시 읽을 수 있어야 한다. 회차 탐색은 수치를 과장하는 spring을 사용하지 않는다.

## Main 반영·중복 방지

- 계획에 선택한 월의 `정기 원금 + 이자`를 주거비에 합산한다. 원금은 자산 수익으로 더하지 않는다.
- 대출 계획이 있으면 기존 `housingInterest` 답변은 **원본을 남기고 합산에서 제외**한다. 새 납입액과 이중 합산하지 않는다.
- 처음 조건을 저장하기 전에 월세·기타 주거비에 섞어 입력한 대출을 사용자가 빼도록 확인한다. 섞인 금액을 자동 추정하지 않는다. 실제 분리는 부모 지출 내역에서 한다.
- 조건 저장은 지출 **초안** 저장이다. `지출 내역으로` 돌아가서 `이 금액으로 반영`할 때 주거비·생활비와 lastApplied를 원자적으로 변경한다. 수입·저축·투자, 다른 앱과 보존 slice는 유지한다.
- 선택 월을 바꿔도 최종 반영 전 Main 금액은 변하지 않는다. 달력이 넘어갔다는 이유로 Main을 자동 갱신하지 않는다.
- 만기 원금은 반복 주거비에서 제외하고 대출 결과·선택 만기월의 지출 검토·Main 요약에 별도 의무로 표시한다. 만기월 지출 검토에서 정기 지출+만기 원금 합계도 보여준다.
- `은행 납입액과 다를 때`에서 선택 월의 실제 정기 납입액을 입력 후 명시 적용한다. 원금/이자 분해와 대출 잔액은 여전히 예상값이며 보정액으로 조작하지 않는다. 월/조건이 바뀌면 보정을 해제한다.
- Main 주거비를 직접 편집해도 대출 조건은 유지한다. 마지막 계산 주거비와 현재 Main 금액이 다르면 반영 확인 상태로 표시한다. 수동 총액에 대출을 몰래 더하지 않는다.

## 저장·호환성

workspace **v5**, 서버 **protocol 5**, 다섯 Main 금액, 기존 13개 질문 ID와 whole-workspace replacement 계약을 유지한다. 지출 도우미 내부에만 schema 2를 도입한다.

```text
expenseAssistant.schemaVersion = 1 | 2
  draft.answers / step / updatedAt       기존 계약
  draft.housingLoans                    schema 2에서 필수
    month                               주거비에 적용할 월
    loans[]                             조건만 저장, 일정은 재계산
    paymentOverrideWon                  선택 월 실제 납입액 또는 null
  lastApplied                           기존 null/적용 snapshot
    answers / appliedAt / housingLoans  반영 시 조건 snapshot도 저장
```

- 필드 부재는 schema 1, null은 수동 이자, 빈 loans는 대출 없음. schema 2로 최초 전환한 초안은 이전 schema 1의 lastApplied를 유지할 수 있다.
- v1 기록은 변경 없이 읽고 보존하며, 명시적인 대출 조건 저장에서만 v2로 전환한다. migration은 기존 행을 재작성하지 않는다.
- v2 이후 구 v1 지출 쓰기는 거부한다. 구 클라이언트는 새 형식 계정에서 새로고침해야 한다. 일반 Main/다른 앱 쓰기는 도우미를 보존한다.
- 기존 백업 format 4, 계정 캐시 v3, 미전송 복구 경로를 사용한다. 새 앱은 구 백업과 새 중첩 버전을 모두 검증한다. 구 앱은 새 중첩 형식 백업을 읽을 수 없다.
- 모든 slice가 유효한 whole-workspace 명시 복원만 원자적 교체가 가능하다. `locations`와 `accountMap`은 변경하지 않는다.
- 서버도 동일 조건·범위·합계를 검증하고 CAS/receipt로 적용한다. 완료 응답 유실은 같은 mutation으로 확인한다. 충돌 재적용은 최신 수입·저축·투자를 보존한다.
- 복구 초안 제거 시 답변뿐 아니라 대출 조건도 비교한다. 오래된 응답이 더 새 대출 입력을 지우면 안 된다.
- 진행 단계만 이동하거나 조회한 뒤 닫는 행동은 미저장 금융 변경으로 취급하지 않는다. 실제 조건 입력 중에는 폐기 확인과 beforeunload 보호를 한다. 완성해 저장을 시도한 조건은 기존 복구 경로에 남긴다. 저장 전 불완전한 개별 폼은 세션 내에서 유지하며 브라우저 강제 종료 복원 대상은 아니다.

## 검증·배포

타입, 계산·저장·백업·복구 단위 테스트, TS/SQL 일치·권한·CAS/receipt DB 검사, 전체 E2E와 390/768/desktop 시각 검증을 수행한다. 응답 유실·충돌·보정·초점·조회 종료를 별도로 확인한다. 실행 결과는 [검증 기록](../evidence/2026-09-28-housing-loan-planner.md)을 따른다.

배포는 [migration](../../../supabase/migrations/202609280001_housing_loan_planner.sql)을 **서버에 먼저 적용한 뒤** 프론트엔드를 배포한다. 적용 전에는 새 UI를 운영 배포하지 않는다. v2 기록이 생긴 뒤에는 구 클라이언트/구 validator로 단순 롤백할 수 없으므로 데이터 보존 후 수정 배포한다.

## 후속 연결

Simulation은 현재처럼 Main 저축·투자액만 읽는다. 대출 완납으로 생기는 여유를 자동 투자하거나, 대응 주택/보증금 자산 없이 부채만 빼서 순자산이라고 부르지 않는다. 만기 재원(보증금 반환/별도 자금/투자 인출), 반환 시점, 부족분과 완납 후 배분은 다음 설계에서 확정한다. 같은 자금을 상환 재원과 계속 투자되는 자산에 중복 사용하지 않는다.
